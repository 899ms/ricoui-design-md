## データ境界

| 保存先            | 保存するもの                                                                             | 保存しないもの                 |
| ----------------- | ---------------------------------------------------------------------------------------- | ------------------------------ |
| IndexedDB         | ローカルワークスペース、アカウントキャッシュ、同期キュー、設定、ローカル AI プロファイル | 永続的なクラウドバックアップ   |
| Supabase Postgres | クラウド Markdown、メタデータ、使用量、リリースメタデータ、トゥームストーン              | AI API キー、ZIP バイト列      |
| Supabase Storage  | サーバー生成の非公開納品 ZIP                                                             | 任意のユーザーアップロード     |
| Vercel            | リクエスト時のアプリケーション実行                                                       | 永続的なドキュメントストレージ |

## シークレットとログ

公開設定には Supabase URL／publishable key、Turnstile Site Key、GA4 Measurement ID が含まれます。Supabase サーバーシークレット、service-role フォールバック、SMTP 認証情報、Google secret、Resend key、セッショントークン、Magic Link、署名付き URL は機密として扱ってください。ソース、Issue、スクリーンショット、分析、ログ、信頼できない Preview 環境に置いてはいけません。

認証情報の漏えいが疑われる場合は、まずプロバイダーでローテーションし、該当する環境スコープだけを更新して再デプロイし、実フローを確認した後に古い値を無効化します。

## 容量と制御

Supabase のデータベース／Storage 使用量、メール配信、Auth ログを毎週確認します。プロバイダー容量の 70% は調査開始、80% は警告、85% は容量回復まで `cloud_controls` で新しい利用を停止する目安です。上流の上限を避けるためだけにユーザーデータを削除してはいけません。

## バックアップと復旧

ユーザーは `DESIGN.md` と必要な派生ファイルをエクスポートする必要があります。管理者は Postgres と非公開 `design-releases` オブジェクトを対応するメタデータとともにバックアップします。復旧ではデータベース構造／データを先に戻し、次にオブジェクトを戻して RLS と所有権を確認し、最後にテストアカウントで署名付きダウンロード、同期、新しいリリース作成をテストします。SQL のインポートに成功しただけでは、復旧の受け入れとはいえません。

アカウント削除では、アプリケーションデータ、非公開リリースオブジェクト、Auth ユーザーを削除する必要があります。部分失敗は再試行可能でなければなりません。納品リリースはソースごとに新しい完了済み 2 バージョンを保持し、公開共有リンクではありません。
